# Image scaling paths in the base-repository stack (MEAS-1)

Owner: solution architecture.
Status: measurement report. Everything below was measured on a headless container with the Rocky
Linux 10.2 userland (a rebuild of the RHEL 10.2 sources), not on RHEL 10.2 itself; the package
versions and the absence of Pillow/ImageMagick must be confirmed on the RHEL machine. The items that
need the reference machine's real display and GPU are listed in section 8 with copy-paste commands.

## 1. Question and short answer

Which ways of scaling a picture to the monitor's real resolution (aspect ratio kept) exist in the
GTK4 / GdkPixbuf / PyGObject stack shipped in the RHEL 10.2 base repositories (BaseOS, AppStream),
what do they cost, and what quality do they give? (Measured on the Rocky 10.2 rebuild, see section 2;
RHEL 10.2 itself has not been checked.)

- **Lanczos is available, but not where one would look.** GdkPixbuf, cairo and GTK itself have no
  Lanczos filter, and none of their documentation names one (pixman's public header lists Lanczos-2/3 kernels, but
  none of GdkPixbuf, PyGObject or the cairo API exposes them). The only Lanczos reachable from the
  GTK / GdkPixbuf / PyGObject stack is the `lanczos` method of the GStreamer `videoscale` element
  (`gstreamer1-plugins-base`, which `gtk4` already depends on, so it adds no new package).
  A separable Lanczos-3 in `python3-numpy` (own code) also works but is about 15x slower.
- **"Better than Lanczos" cannot be promised:** no path in the base repositories documents one.
- **Do not rely on `Gtk.Picture` / a plain texture for big downscales.** On the GL renderer a
  texture drawn at less than half its size is mip-mapped automatically; the result is measurably
  blurrier and aliases fine patterns more than an area-average, see section 5.
- Recommendation (section 7, valid for the Rocky 10.2 rebuild until section 8 step 1 confirms the
  RHEL 10.2 versions): scale on the CPU to the exact device-pixel size with
  `videoscale method=lanczos envelope=3`, show the result 1:1; fall back to
  `GdkPixbuf` `BILINEAR` if GStreamer cannot be used.

## 2. Method and environment

- Stack: Rocky Linux 10.2 userland (a rebuild of the RHEL 10.2 sources) with only `baseos` and
  `appstream` enabled, run unprivileged in a user namespace on a 2 vCPU x86-64 container, shared with
  other workloads (load average 1.5 to 2.6 during the final run, so absolute times have roughly
  +-15 % noise; an earlier run of the same scripts agreed within that). RHEL 10.2 itself was not
  available, so the package versions below are those of the rebuild; the reference machine must
  confirm them (section 8, step 1).
- Versions measured: `gtk4 4.16.7-4.el10`, `gdk-pixbuf2 2.42.12-4.el10_1.5`,
  `cairo 1.18.2-2.el10_2.1`, `pixman 0.43.4-2.el10`, `python3-gobject 3.46.0-7.el10`,
  `python3-cairo 1.25.1-5.el10`, `python3-numpy 1.26.4-7.el10_2`,
  `gstreamer1 1.26.7-5.el10`, `gstreamer1-plugins-base 1.26.7-2.el10_2.2`,
  `netpbm-progs 11.09.00-1.el10`, `mesa-dri-drivers 25.2.7`, Python 3.12.13.
  No EPEL, CRB or third-party repository was used.
- Documentation evidence is taken from the files shipped for exactly these versions: the GIR files
  of the `-devel` packages, `cairo.h`, the output of `gst-inspect-1.0 videoscale` and the source
  RPMs of the same builds. "Source" below means the source RPM of the measured build.
- Input: a synthetic, deterministic scene generated by `tools/measure-scaling/scene.py` (Siemens
  star, line gratings, step edges, text, smooth noise texture). It is rendered natively at every
  size, so a *reference image at the target size* exists. Real photographs may behave differently;
  `target_check.py` accepts one (section 8).
- Every path receives the same decoded RGB `GdkPixbuf` and returns an RGB image. The timed region is
  everything between "decoded pixbuf" and "pixels ready to upload" (including, for cairo, the
  pixbuf-to-surface conversion of about 55 to 70 ms at 24 MP). Repetitions, per row type: the
  `bench.py` rows (section 4 first table) are the median of 5 runs for A and C and of 15 runs for B
  and D, after one warm-up, except the numpy row, which is the median of only 2 runs (that is, their
  mean); the JPEG rows of `load_bench.py` are the median of 3 runs, the PNG rows of 2 runs; the
  `pamscale` rows, the GStreamer first-use rows and the peak-RAM column are single runs. The CPU time
  is recorded too (see the multi-threaded GStreamer row).
- Cases: **A** 6400x3600 (23 MP) -> 2560x1440; **B** 800x450 -> 2560x1440 (3.2x up);
  **C** 6000x4000 (24 MP, 3:2) -> 2160x1440; **D** 800x600 -> 1920x1440 (aspect-kept fit).
  Quality is evaluated on A and B, where the reference image exists.

## 5. Quality

Reference = the same scene rendered natively at 2560x1440. PSNR (dB, higher is closer to the
reference) per region; "over/under" are the levels by which a 64 -> 192 step edge overshoots on the
bright and dark side (0 = no ringing); "rise" is the 10 to 90 percent edge width in pixels (the
reference itself is 1.49).

**Caveat on the metric:** the reference is a coverage-antialiased render, which is itself an area
average, so PSNR favours area-average filters (pixbuf BILINEAR, cairo GOOD) and penalises sharper
ones for detail the 2560-pixel grid cannot represent. Use PSNR to rank artefacts, not sharpness; the
sheets in `samples/` are what a viewer sees.

For an enlargement the reference holds detail that the small source never had, so all PSNRs sit
near 22 dB; the ranking and the ringing column are the useful part.

Observations (each is visible in `samples/`):

1. **Reduction: area-average filters are clean, point-like ones alias.** NEAREST, gst bilinear
   (2-tap, no area integration) and gst 4-tap show moire at the star centre and in the 2 to 3 pixel
   gratings; pixbuf BILINEAR, cairo GOOD, catrom and the Lanczos variants do not.
2. **Lanczos is crisper and rings.** Lanczos-3 overshoots a 128-level step by about 7 levels on a
   reduction and 9 / 17 levels on a 3.2x enlargement (visible as a thin halo in
   `upscale-step-edge-4x.png`); catrom rings less (3 / 4 and 2 / 10), Mitchell least.
3. **Enlargements:** bilinear (pixbuf, cairo, GL, gst) is soft; Lanczos-3 and catrom are sharper
   with halos; cairo BEST turns blocky above 2x; gst 4-tap rings by 30 to 35 levels.
4. **`Gtk.Picture` on the GL renderer** (default texture node) produced pixel-identical output to
   an explicit TRILINEAR for the 2.5x reduction (the automatic mip-map), and is softer and aliases
   the 3 pixel gratings more than an area average (gratings PSNR 19.3 against 31.0). The 2-tap
   explicit LINEAR scores better on the gratings here, but a 2-tap filter drops pixels and shows
   moire at the star centre; neither is an area average.
5. **The GStreamer scaler is not an exact Lanczos.** `videoscale` quantises its taps to 6 bits for
   8-bit video (`#define LQ` in `video-scaler.c`). Against the independent double-precision numpy
   implementation, `lanczos env=3` differs by 0.17 levels on average (maximum 12) on A and by 0.30
   (maximum 28, on hard edges) on B. A visible consequence: at the exact 2.5x reduction of case A,
   `catrom` and `lanczos` with the default envelope produced bit-identical images. Treat the name as
   "Lanczos as implemented by `videoscale`", not as a bit-exact reference.

## 6. Other findings that affect the display code

- PyGObject 3.46.0 (the version on this stack) cannot marshal `Gsk.RenderNode`:
  `Gtk.Snapshot.to_node()` raises `TypeError: No means to translate argument or return value for
  'GskTextureNode'`. Drawing from a widget's `do_snapshot` works (it only passes textures and
  rectangles); offscreen rendering of a node from Python needs `ctypes`
  (`capture_ngl.py` does that for the measurement).
- The automatic mip-mapping of a plain texture node is on by default in the `ngl` and `vulkan`
  renderers (source: all GPU optimizations are enabled unless `GSK_GPU_DISABLE=mipmap` is set or the
  GL context lacks support). Whether the reference machine's GPU context keeps it on is a section 8
  item.
- `Gdk.cairo_set_source_pixbuf` is usable from PyGObject here (pixbuf to cairo surface in C).
- A GTK4 client runs against `mutter --headless --virtual-monitor 2560x1440` in the container, with
  both the cairo renderer and the GL renderer (via software GL). That made the `Gtk.Picture`
  measurements and the `target_check.py` run possible, and may be reusable for automated Wayland
  smoke tests. `gnome-shell` and `systemd-logind` were not tried.

## 7. Recommendation

1. **Pre-scale on the CPU to the exact device-pixel size and show the texture 1:1.**
   `videoscale method=lanczos envelope=3` (path 9) costs about 90 ms for a 24 MP picture on the
   measurement container (about 65 ms with `n-threads=2`), +31 MB of RAM, and needs no package
   beyond `gtk4`. Run it on the next picture in a worker thread while the current one is shown, so
   the cost is hidden. Compute the target size as `round(logical size * surface scale)` (use
   `Gdk.Surface.get_scale()`).
2. **Say "Lanczos-3" only for this path**, and describe it as the GStreamer `videoscale` Lanczos
   with envelope 3. Do not promise anything "better".
3. **Fallback** if GStreamer is unusable (missing plugin, caps negotiation failure): `GdkPixbuf`
   `scale_simple(BILINEAR)`, about 66 ms, area-average on reduction, soft on enlargement. Log the
   fallback at WARNING level, following `docs/logging-and-lifecycle.md`.
4. **Enlargements:** the choice between Lanczos-3 (crisper, halo of about 7 to 13 percent of a step on an enlargement) and
   Catmull-Rom or Mitchell (less ringing) is a matter of taste for the reference machine's owner;
   `samples/upscale-*.png` shows all of them side by side. Both are one `method=` string.
5. **Avoid:** cairo `BEST` (about 1.1 s at 24 MP, blocky enlargements), `GDK_INTERP_HYPER`
   (deprecated and worse than BILINEAR), `new_from_file_at_scale` (bilinear only, cannot be
   combined with Lanczos), and a bare `Gtk.Picture` for large downscales. `pamscale` and the numpy
   path are not worth their dependencies.
6. Not measured, but a known property of all these paths: they filter gamma-encoded values, not
   linear light. `videoscale` has a `gamma-mode` property that was not evaluated.

## 8. Not measured here, and how to measure it on the reference machine

Not measurable in the headless container: the real GPU path (frame times, upload cost, the actual
look of GPU mip-mapping), CPU timings on the reference CPU, behaviour with fractional display
scaling, and real photographs. All commands use only AppStream packages. Run them in the GNOME
session on the reference machine.

```bash
# 1. Confirm the package versions match the ones measured here (paste the output back)
rpm -q gtk4 gdk-pixbuf2 cairo pixman python3-gobject python3-cairo \
    gstreamer1-plugins-base mesa-dri-drivers; grep -m1 'model name' /proc/cpuinfo; nproc

#    Confirm that the negative package claim of section 3 also holds on RHEL 10.2
#    (expected: nothing found for any of them)
#    Glob names, plus a positive control that MUST be found, so that a typo or a blind query cannot
#    pass as "nothing found". Expected output: exactly one line, python3-numpy.
dnf -q repoquery --qf '%{name}' 'python3-pillow*' 'ImageMagick*' 'vips*' 'opencv*' 'gegl*' \
    python3-numpy | sort -u

# 2. Get the tools
sudo dnf install -y git python3-gobject python3-cairo python3-numpy gstreamer1-plugins-base
git clone https://github.com/trensoft/slideshow-lock.git && cd slideshow-lock/tools/measure-scaling

# 3. CPU costs on this machine (about 3 minutes, close other applications first)
python3 bench.py A --out out && python3 bench.py B --out out
python3 -c "import json;[print(k, v.get('median_ms')) for k, v in json.load(open('out/results_A.json'))['paths'].items()]"

# 4. Real display and GPU: opens a fullscreen window, cycles five modes for 4 s each and prints
#    frame-time statistics plus the renderer in use. Space = next mode, Q = quit.
GDK_DEBUG=opengl python3 target_check.py 2>&1 | tee target_check.log
#    Same with one of your own photographs (it never leaves the machine):
python3 target_check.py ~/Pictures/some-photo.jpg
```

What to look at in step 4: mode 0 is the path a plain `Gtk.Picture` takes (a texture node, linear
filtering plus automatic mipmaps for a big reduction); modes 1 and 2 are the same texture with an
explicit LINEAR or TRILINEAR filter; modes 3 and 4 are the CPU pre-scaled pictures shown 1:1. Compare
fine detail (foliage, text, hair, brick or fabric patterns). Report: the renderer name printed
(`NglRenderer` expected), whether modes 0 to 2 look softer or shimmer compared with mode 4, the
printed `max` frame times (a first-frame stall in modes 0 to 2 is the texture upload), and which of
modes 3 and 4 looks better. Notes: the frame statistics cover only the automatic pass, so do not
press Space until "Automatic pass done" is printed (about 25 seconds including the picture loading);
afterwards Space flicks between the modes by eye, and `bench.py` uses the fixed target sizes of section 2,
not the reference monitor's native resolution.

## 9. Reproducing the measurements in the container

`tools/measure-scaling/` holds the scripts that produced the cost tables, the quality tables of
sections 4 and 5 (except the points listed below) and the sheets: `scene.py` (test scene), `bench.py` (cases A to D),
`prep_c.py`, `load_bench.py`, `rss_one.py` (24 MP JPEG decode, scale-on-load, `pamscale`, memory),
`capture_ngl.py` (GL renderer output through `ctypes`, run as a client of a compositor) with
`gl_metrics.py` (PSNR, overshoot and edge rise of its output, the "GL" rows of section 5; it is a
cleaned-up rewrite of the one-off script that produced those rows and has not been re-run in this
form),
`sheets.py` (the PNG sheets), `target_check.py` (section 8) and `run-cpu.sh` (the whole CPU part).
The sheets in `samples/` were produced by these scripts: crops at 1:1 (the edge sheets at
4x nearest-neighbour zoom), each tile labelled with its path and median time.

Not reproducible from the repository (obtained with short one-off scripts whose raw output was not
kept): the GStreamer first-use timings, the numpy-versus-`videoscale` difference figures of
section 5 item 5, the `catrom` versus `lanczos` identity check, and the statement that an earlier
run of the benchmark agreed within about 15 percent. To redo them: time `Gst.init(None)` and the
first `appsrc ! videoscale ! appsink` pipeline in a fresh process (delete
`~/.cache/gstreamer-1.0` for the cold registry), and compare the saved `out/*_numpy_lanczos3*.npy`
and `out/*_gst_lanczos_env=3.npy` arrays pixel by pixel. The raw `out/results_*.json` of the final
run were not committed either; `run-cpu.sh` regenerates them.
